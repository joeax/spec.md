# SPEC.md Create Plan Skill

Use this skill to turn a SPEC.md document's requirements into an actionable, self-contained implementation plan. This is an extension skill, not part of the core specmd workflow — it is not required to read, define, or sync a spec, and a project is free to use its own planning skill instead.

## Core principles

- Prefer evidence from the repository over assumptions.
- When information is missing or ambiguous, make the smallest reasonable assumption and state it clearly.
- If a change would materially affect scope, architecture, or implementation, ask the user for confirmation before proceeding.

## Dependencies

This skill extends `specmd` and requires it to be installed. Before planning, confirm the `specmd` skill is available. If it isn't, stop and tell the user to install it first (see the specmd skill's setup instructions) rather than reading its schema files directly.

## Required reading order

Before planning, use the specmd skill's Read function to load the source SPEC.md file — it resolves the core schema, the spec (or custom/extended) schema, frontmatter, and body for you. Only pull in additional SPEC.md files if they're clearly in scope, again via the specmd skill.

## Plan

Intent: Turn a focused portion of a SPEC.md document into an actionable implementation plan.

Use this function when the user needs a plan before changing code, especially when the request is scoped to a subset of the spec such as a feature, module, API surface, or a specific set of requirements.

Steps:
1. Identify the scope of the request. If the user asks for a plan for specific sections or a focused change, limit the plan to that scope rather than the entire spec.
2. Follow the Required reading order above for the relevant SPEC.md file. Also inspect the current codebase for the requested scope to determine what's already implemented, partially implemented, or missing — this determines each task's initial status marker ([X]/[P]/[ ]/[D]/[C]) rather than assuming everything is unstarted.
3. Read the plan schema file so the generated plan document follows the expected structure.
4. Break the requested work into clear, ordered implementation steps that can be executed in chunks or iteratively, each assigned a stable, sequential ID (`**T01**`, `**T02**`, ...) that later execution can reference.
5. Create a markdown plan document in the `.specmd/` folder that stands on its own: an implementation agent must be able to execute it without loading SPEC.md or this skill. If `.specmd/` already contains other plan documents, make sure the new one is clearly distinguishable from them (via filename, `description`, and `state`) so it's unambiguous which plan an implementer should run.
6. Keep the plan focused on the requested change and call out assumptions, risks, or unresolved details.

Output: a self-contained markdown plan document, scoped to the user's request, that an implementation agent can execute without further reference to SPEC.md or this skill.

## Working guidelines

- Avoid creating or editing files beyond the plan document itself.
- Keep outputs structured and useful for downstream implementation, preferring bullet points over prose paragraphs.
- When creating the plan's frontmatter, populate only fields the plan schema defines — never invent custom top-level fields.
- In the plan's `metadata`, populate only objective, verifiable fields the schema defines (e.g. a generated date) — never `author`, and never `updated`, unless the user explicitly provides an author name or the agent has its own identity to attribute.
