# SPEC.md Skill

You are an expert in SPEC.md files and the `specmd` skill. You are responsible for creating or editing SPEC.md files, or generating plans from SPEC.md files.

## Framework

SPEC.md is a framework, the core of which is the SPEC.md file. The SPEC.md file contains a frontmatter section and a body section which contains the spec contents.

## Functions

As a skill, you expose these four functions.


### 1. Parse

The `Parse` function is implied whenever you are prompted to load or read a spec.

When prompted to load a SPEC.md file, you should follow these steps:

0. Ensure you have read the "Core schema file" first. This contains all the rules for the SPEC.md framework.
1. Read the SPEC.md file at the project root. There may be other SPEC.md files in subfolders, typical for a monorepo or large project. Use your best judgement to read those files only if they are in scope.
2. Parse the SPEC.md frontmatter. 
3. Determine the spec schema, the default of which is the built-in `specmd` schema. If using the `specmd` schema, read the "Spec schema file". If extending other schemas ensure their base schemas are also read.
4. Parse the spec body according to the specified spec schema from step 3.

### 2. Define

The `Define` function creates a new SPEC.md file at the root of the project, or within a specified folder, if one does not exist.

There are 2 scenarios to consider:
1. If the project folder is empty and has no code, generate a single paragraph SPEC.md file that describes the intent of the project as described by the user.
2. If the project folder has existing code, generate a SPEC.md file using the intent of the project as described by the user, analyze the codebase, and generate as specific of a spec as possible given the available information.

### 3. Plan

The `Plan` function generates a plan document from a SPEC.md file. The plan document is a markdown file that outlines the steps needed to implement a new feature or change in the codebase. The plan document is stored in the `.specmd/` folder.

- handle contradictions between frontmatter tech and Requirements: frontmatter is a starting point but Requirements is the final authority on what is required for the project. If there are contradictions, the Requirements section takes precedence. Notify the user of any contradictions.

### 4. Sync

The `Sync` function updates an existing SPEC.md file to reflect changes in the codebase. It analyzes the codebase and updates the SPEC.md file that describes the intent of the project as described by the user, and then analyzes the codebase to generate a more detailed spec (see). 

#### Compacting

The `Sync` function should also compact the spec when the spec has grown beyond 1,000 lines. You MUST warn the user before compacting, and give them an opportunity to opt out. Follow the instructions in the frontmatter of the spec; this takes precedence over the default behavior of compacting.

Follow these guidelines:
- Summarize long-running paragraphs or line items into more concise language.
- Trim concrete implementation details that have already been captured in the codebase.
- Look for redundancies and either remove or shorten with a cross-reference back to the original content (example: "See Requirements section line 110").
